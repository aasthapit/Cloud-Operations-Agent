1Personas and entry points

Every flow starts from one of four personas and the state the system finds them in. The console never asks for anything it can resolve itself; the frames below show exactly where it asks, and why.

PersonaEntry stateTypical openingPrimary flows
App developerOne registered application“Why is payments-api flaky in prod?”F1, F5, F7
SRE / platform engineerMany registered applications, deep platform knowledge“Is my stuff healthy?” / “attest prod-east-2”F2, F4, F6
New team memberNo registered applications“Why is my app slow?”F3
OperatorEdits the config plane, not the chatEdits checks/app360.yamlF9

The ops manager persona from the PRD consumes the exported reports produced in F7 rather than driving conversations. Frames are drawn at desktop width; wide frames scroll horizontally inside their panel.

2The turn lifecycle

Every flow is a path through the same turn skeleton. Two gates are enforced by the agent runtime in code, not by prompt (PRD decision D1): the context gate (know the user, application, and clusters before analysis) and the attestation gate (fresh platform health before any answer).

F8Failure and degraded modes

Honesty rules the failure UX: partial results are labeled, absent trust is named, and nothing is invented to fill a gap. Because the check phases are deterministic code (D1), most failures degrade a report instead of killing the turn.

FailureWhat the user seesGuarantee
One check's tool times out or errorsThe battery completes; that check's row renders error with the failure reason; overall status treats it as unknown, not passedFR-GW-6..7: structured tool errors, batteries never abort on one check
Cluster monitoring untrustworthy (Watchdog absent, monitoring operator degraded)Verdict unattestable, visually distinct from degraded; the agent says platform health cannot be confirmed and caps its confidenceFR-ATT-5: absence of signal is never reported as health
Ollama unreachableAttestation and Application 360 cards still arrive; the narrative slot carries an unavailability notice with a correlation id (frame below)D1 dividend: deterministic value survives model outages
Gateway unreachableThe turn fails fast with a plain-language error and correlation id; no cards, no guessesFR-CHAT-2: no fabricated fleet state, ever
Invalid config deployed by an operatorConversations continue on the last known good battery; the operator sees the validation error (F9)FR-CFG-3: user-facing behavior never breaks on a bad edit

F9.1Check tuning is a YAML edit, not a deploy. The added check names a tool, templated args, a rule, a severity, and a runbook 1; the watcher validates and swaps atomically, announcing the new battery and version 2, which the console's checks card reflects for every user 3. A bad edit is rejected with the exact rule named (“rule 7: expected number, got '3O'”) while conversations continue on the last known good battery; prose prompts skip the machinery entirely and are re-read at every LLM call.
