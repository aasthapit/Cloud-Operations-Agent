1Personas and entry points

Every flow starts from one of four personas and the state the system finds them in. The console never asks for anything it can resolve itself; the flows below show exactly where it asks, and why.

PersonaEntry stateTypical openingPrimary flows
App developerOne registered application“Why is payments-api flaky in prod?”F1, F5, F7
SRE / platform engineerMany registered applications, deep platform knowledge“Is my stuff healthy?” / “attest prod-east-2”F2, F4, F6
New team memberNo registered applications“Why is my app slow?”F3
OperatorEdits the config plane, not the chatEdits checks/app360.yamlF9

The ops manager persona from the PRD consumes the exported reports produced in F7 rather than driving conversations.

2The turn lifecycle

Every flow in this document is a path through the same turn skeleton. Two gates are enforced by the agent runtime in code, not by prompt (PRD decision D1): the context gate (know the user, application, and clusters before analysis) and the attestation gate (fresh platform health before any answer).

F1First contact, happy path

Persona: app developer, one registered application. Precondition: signed in; payments-api runs in prod-east-1 and prod-east-2. The defining property: from a single vague sentence to evidence-backed answers with zero questions asked.

Storyboard · F1app developer
1
You
Why is payments-api flaky in prod?
2✓ Context resolved · payments-api · prod · 2 clusters
3✓ Health attestation · prod-east-1, prod-east-2 · 3.1s
Cluster attestationhealthy degraded
4✓ Application 360 · 31 checks · 4.6s
Application 360 · payments-api payments-prod @ prod-east-2at risk
5
Agent
Summary: two overlapping causes: your pods are OOMKilled under load, and prod-east-2 is mid node-maintenance with a degraded ingress operator amplifying restarts. Next step: raise the memory limit toward 768Mi; escalation not warranted yet…

What happened

  1. 1One vague sentence is enough; the thread id is minted here and follows every log and span. NFR-OBS-2
  2. 2Identity claims name the user; the registry maps them to payments-api; Prometheus discovery finds where it actually runs. No questions asked because nothing is ambiguous. FR-CTX-1..3
  3. 3Attestation battery runs per cluster, concurrently; the card renders from typed JSON, not prose. FR-ATT-1, FR-UI-2
  4. 4Application 360 runs automatically once context exists; progress streams while checks execute. FR-360-1, FR-CHAT-4
  5. 5Only now does the LLM speak, grounded in the check JSON; the platform-vs-app split is explicit. FR-360-4, FR-CHAT-3
Outcome: question to evidence in under 10 seconds of checks plus streamed narrative; both report cards remain in the thread for drill-down (F7).

F2Ambiguous context, one clarification

Persona: SRE with six registered applications. The context gate refuses to guess and refuses to interrogate: exactly one question, options enumerated, then straight into the F1 path.

Storyboard · F2SRE · 6 apps
1
You
Is my stuff healthy?
2
Agent
You have six registered applications. Which one first?
1 checkout2 loyalty3 refunds4 catalog5 pricing6 audit-log
3
You
checkout, prod
✓ Context resolved · checkout · prod · 3 clusters
✓ Health attestation · 3 clusters · 4.2s
✓ Application 360 · 31 checks · 5.0s
4
Agent
All three prod clusters attest healthy; checkout is serving normally. One thing worth a look: p95 latency crept 12% this week…

What happened

  1. 1“My stuff” resolves to six candidates; the gate stops before running a single check against the wrong scope.
  2. 2One question per turn, options as quick-picks; this is the A2A input-required state rendered as a normal chat turn. FR-CTX-4, FR-UI-5
  3. 3Free text or a click both work; the answer folds into session state so the question is never re-asked this thread. FR-CTX-6
  4. 4From here the flow is F1; an SRE gets the same discipline, just denser evidence.
Outcome: ambiguity costs exactly one turn; nothing runs against a guessed scope.

F3Unregistered user, onboarding

Persona: new team member whose identity maps to no registered application. The agent explains itself instead of failing, and still helps if the user names an application (visibility beats ceremony in triage).

Storyboard · F3new team member
1
You
Why is my app slow?
2
Agent
Your account has no registered applications yet, so I cannot resolve what “my app” means. Your team lead can register you in the application registry (owner group mapping). If you tell me the application name, I can proceed now and note it is outside your registered set.
3
You
It's inventory-sync
⚠ Proceeding on user-named app · not in your registered set
✓ Placement found · inventory-sync · nonprod-east-1
✓ Attestation + Application 360 · 6.8s
4
Agent
inventory-sync runs in nonprod-east-1 (attests healthy). Its pods are healthy but the sync CronJob has missed 3 of its last 5 schedules…

What happened

  1. 1No claims-to-application mapping exists; running checks blind would be noise.
  2. 2Onboarding guidance names the fix (registry entry) and offers a working path forward. FR-CTX-5
  3. 3A user-named app is honored but visibly flagged; Prometheus discovery still verifies it exists before anything runs. FR-CTX-2
  4. 4Full triage proceeds; the registered-set caveat stays attached to the thread.
Outcome: a brand-new user gets value on day one and learns the registration path in the same turn. An absent or malformed identity (no claims at all) gets guidance only, with no checks executed. FR-ID-4

F4Platform-attributable incident

Persona: SRE (or any user) whose symptom is actually the platform. The attestation running first is what makes this flow cheap: the reframe arrives before any application digging, with the escalation evidence already assembled.

Storyboard · F4SRE
1
You
checkout is throwing 503s in prod-west
✓ Context resolved · checkout · prod-west-4
2⚠ Health attestation · prod-west-4 · 2.9s
prod-west-4 ingress operator degraded · MCP worker updating 3/9 · 2 nodes cordoneddegraded maintenance
3
Agent
Platform first: prod-west-4's ingress operator is degraded while worker nodes roll for maintenance; 503s at the router are expected symptoms and checkout's own pods look healthy. This is platform-attributable. Escalate to the platform team with: ingress ClusterOperator Degraded since 13:41, router pod restarts on cordoned nodes, MCP worker 3/9, and your route's 503 rate. Want me to keep checking checkout while the roll completes?

What happened

  1. 1Explicit cluster in the question narrows scope without a clarification turn. FR-CTX-7
  2. 2The attestation distinguishes degraded (ingress operator) from expected maintenance (MCP rolling, cordoned nodes) instead of shouting one combined alarm. FR-ATT-4
  3. 3Attribution is explicit and the escalation package lists concrete evidence the platform team will want; the agent does not pretend it can fix the platform. FR-CHAT-3, FR-CHAT-6
Outcome: no wasted application archaeology; the user leaves with an evidence bundle and a clear owner. Had the cluster been unattestable (Watchdog absent), the agent would have said monitoring itself cannot be trusted and capped its confidence accordingly. FR-ATT-5

F5Follow-up with stale attestation

Persona: any, later in an existing thread. The attestation gate applies to every turn, not just the first; freshness is a TTL (default 300 s), and changes are surfaced before the actual answer.

Storyboard · F5same thread · 12 min later
1
You
What about memory usage?
2⚠ Attestation stale (12 min > 300 s) · re-attesting 2 clusters
✓ Re-attested · prod-east-2 recovered: ingress healthy, maintenance complete
3
Agent
First, a change: prod-east-2 has recovered since we last checked; the ingress operator is healthy and the node roll is complete. On memory: payments-api p95 usage is 497Mi against a 512Mi limit; two containers were OOMKilled in the last hour. The platform recovery will not fix that headroom problem…

What happened

  1. 1The user just asks; freshness bookkeeping is invisible until it matters.
  2. 2TTL exceeded, so the runtime re-attests before answering; the delta (recovered!) is computed against the cached verdicts. FR-ATT-7
  3. 3The change leads the reply, then the actual question is answered from a fresh obs__query; conclusions never rest on stale platform state. FR-CHAT-2
Outcome: long-running incident threads stay trustworthy; every answer stands on platform state at most TTL-old.

F6Direct cluster attestation

Persona: SRE working the platform itself. A cluster-scoped ask needs no application context; the fleet resolver turns any reasonable name into an exact cluster before anything runs.

Storyboard · F6SRE
1
You
attest prod-east-2
2✓ Cluster resolved · prod-east-2 · region us-east · prod ring
✓ Attestation battery · 12 checks · 2.7s
prod-east-2 version 4.16.9 · all operators available · 41/41 nodes readyhealthy
3
Agent
prod-east-2 attests healthy. Recent changes: the 4.16.9 update completed 14:07, worker MCP settled 14:19, and the ingress operator returned to Available 13:58 after the roll. No critical alerts firing; capacity headroom is normal (CPU requests 61% of allocatable).

What happened

  1. 1An imperative, cluster-scoped ask; the application context gate is satisfied by explicit scope. FR-CTX-7
  2. 2The resolver matches name, alias, label, or fuzzy text across hundreds of clusters and refuses to guess between near-matches. FR-MCP-1..2
  3. 3Beyond the verdict, the answer volunteers what changed recently, which is what an SRE actually opens this tool to learn.
Outcome: the attestation card doubles as a shareable mini status page for one cluster; “attest checkout's clusters” works the same way through app placement.

F7Report drill-down and export

Persona: any user holding a report card; also the path that feeds the ops manager. Cards are data, not prose: every section expands to its checks, every check to its evidence, and the whole report exports as Markdown.

Interaction · F7report card
Application 360 · payments-api payments-prod @ prod-east-2at risk
3. Deployment overviewhealthy
1 ▾ 4. Runtime health · 7 restarts, OOMKilled x2failing
2 check pod-restarts · tool ocp__get_workloads · 14:02:15 observed: 7 restarts / 60 min · threshold: <= 3 · last state OOMKilled (137) evidence: payments-api-6d9c (2 pods) · runbook: KubePodCrashLooping
5. Configuration · 2 fields awaiting inputmanual
12. Capacity · memory limit 512Mi, p95 at 497Miwarning
13 more sectionsexpand all
3Export .mdCopy evidence

What happened

  1. 1Collapsed rows carry name, observed value, and status pill; failing rows sit above the fold. Manual and registry-sourced items render labeled, never silently missing. FR-UI-7, FR-360-6
  2. 2Expanding reveals the evidence trail from the embedded check results: tool, arguments, observed vs threshold, timestamp, runbook link; no re-query needed. FR-360-9
  3. 3Export produces the organization's 18-section Markdown report; “copy evidence” grabs the expanded check's facts for a ticket or escalation. FR-360-7
Outcome: the same artifact serves the developer (drill-down), the escalation (evidence copy), and the review meeting (export); nobody re-runs checks to re-read them.

F8Failure and degraded modes

Honesty rules the failure UX: partial results are labeled, absent trust is named, and nothing is ever invented to fill a gap. Because the check phases are deterministic code (D1), most failures degrade a report instead of killing the turn.

FailureWhat the user seesGuarantee
One check's tool times out or errorsThe battery completes; that check's row renders error with the failure reason; overall status treats it as unknown, not passedFR-GW-6..7: structured tool errors, batteries never abort on one check
Cluster monitoring untrustworthy (Watchdog absent, monitoring operator degraded)Verdict unattestable, visually distinct from degraded; the agent says platform health cannot be confirmed and caps its confidenceFR-ATT-5: absence of signal is never reported as health
Ollama unreachableAttestation and Application 360 cards still arrive (they need no model); the narrative slot shows “analysis unavailable: inference backend unreachable” plus a correlation idD1 dividend: deterministic value survives model outages
Gateway unreachableThe turn fails fast with a plain-language error and correlation id; no cards, no guessesFR-CHAT-2: no fabricated fleet state, ever
Invalid config deployed by an operatorConversations continue on the last known good battery; the operator sees the validation error (F9)FR-CFG-3: user-facing behavior never breaks on a bad edit
Error surface contract

Every user-visible failure carries a correlation id that matches one trace across all five services; stack traces and internal details never reach the console (NFR-LOG-2). The activity log shows the failing phase so the user can tell “my question was misunderstood” from “the platform tooling had a bad minute”.

F9Operator: hot-editing the config plane

Persona: operator. The config plane is a first-class user surface: prompts, routing, skills, batteries, fleet, and gateway registry all change behavior on save, with validation guarding the swap.

Storyboard · F9operator · editor + console
1✎ operator edits checks/app360.yaml · adds check pdb-disruptions
2✓ config.reload · app360.yaml valid · battery 31 → 32 checks · version a41c9e2 → b52d0f3
Next report in any thread section 14 now includes PDB disruptions allowed32 checks
3⚠ operator edits health_attestation.yaml · typo in a threshold
⚠ config.reload rejected · rule 7: expected number, got "3O" · keeping a41c9e2
4✎ operator edits agent/system_prompt.md · tone adjustment
✓ no reload event needed · next LLM call reads the new prompt

What happened

  1. 1Adding a check is YAML, not code: tool, templated args, evaluation rule, severity, runbook URL. D3, FR-360-2
  2. 2The watcher validates against the schema, swaps atomically, and stamps a new config version, visible in the console's left rail. FR-CFG-2
  3. 3A bad edit cannot take the system down: last known good stays active and the error names the exact rule. FR-CFG-3
  4. 4Prose prompts need no machinery at all; they are re-read on every invocation. FR-CFG-2
Outcome: check tuning and prompt shaping are minute-scale config edits with a visible version stamp, satisfying acceptance criteria 5 and 6; adding a whole cloud domain is the same motion at the gateway registry (servers.yaml, NFR-EXT-1).
