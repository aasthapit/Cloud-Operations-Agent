# Research Report: OCP Fleet Health Checks and First-Level Triage Practice

All findings below are grounded in the cited sources; PromQL from kubernetes-mixin was verified against the published mixin rules.

---

## A. CLUSTER HEALTH ATTESTATION

The industry-standard "attest the platform before debugging the app" sequence for OpenShift, in roughly the order Red Hat's own troubleshooting and update docs prescribe.

### A1. ClusterVersion
- **Query:** `oc get clusterversion` / API resource `clusterversion/version` (`config.openshift.io/v1`), fields `.status.conditions[]` with types `Available`, `Progressing`, `Failing`, `Upgradeable`, `RetrievedUpdates`; `.status.desired.version` vs `.status.history[0]` (state `Completed` vs `Partial`). CLI equivalents: `oc adm upgrade` (summary; says "Cluster version is X" when steady, or shows progress/retrieved-updates errors) and `oc adm upgrade status` (4.16+; detailed control plane + worker pool update progress).
- **Healthy:** `Available=True`, `Failing=False`, `Progressing=False` (a `Progressing=True` cluster is mid-upgrade - a maintenance signal, not necessarily unhealthy).
- **Why:** The Cluster Version Operator (CVO) aggregates cluster health; `Failing=True` means the cluster cannot reach desired state and needs admin intervention; `Progressing=True` means an update is rolling out, so degraded operators/nodes may be expected transient states.
- Sources: [Understanding cluster version condition types](https://docs.redhat.com/en/documentation/openshift_container_platform/4.10/html/updating_clusters/understanding-clusterversion-conditiontypes_updating-clusters-overview), [Performing a cluster update (4.18)](https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html/updating_clusters/performing-a-cluster-update), [Troubleshooting a cluster update (4.17)](https://docs.redhat.com/en/documentation/openshift_container_platform/4.17/html/updating_clusters/troubleshooting-a-cluster-update#gathering-data-cluster-update)

### A2. ClusterOperators
- **Query:** `oc get clusteroperators` (columns AVAILABLE / PROGRESSING / DEGRADED / SINCE / MESSAGE); API `clusteroperators.config.openshift.io`, `.status.conditions[]` types `Available`, `Progressing`, `Degraded`. PromQL: `cluster_operator_conditions{condition="Degraded"} == 1`, `cluster_operator_up` (exposed by CVO, used by OCP's own ClusterOperatorDown/ClusterOperatorDegraded alerts).
- **Healthy:** every CO `Available=True`, `Degraded=False`; `Progressing=True` only during an upgrade. `Degraded` means the operator's actual state has persistently not matched required state; `Available=False` means part of the operand is non-functional and requires intervention.
- **Criticality tiering (for triage weighting):** `etcd`, `kube-apiserver` (control plane data/API path - everything depends on them), `kube-controller-manager`, `kube-scheduler`, then `ingress` (app traffic entry), `dns` (in-cluster resolution), `network`, `authentication` (console/oauth logins), `machine-config` (node rollouts), `monitoring` (your observability itself). A degraded `monitoring` CO means the very signals below may be stale.
- Sources: [ClusterOperator conditions dev guide (openshift/enhancements)](https://github.com/openshift/enhancements/blob/master/dev-guide/cluster-version-operator/dev/clusteroperator.md), [Updating clusters overview (4.11)](https://docs.redhat.com/en/documentation/openshift_container_platform/4.11/html/updating_clusters/updating-clusters-overview)

### A3. Nodes
- **Query:** `oc get nodes`; conditions on `.status.conditions[]`: `Ready` (True/False/Unknown - Unknown = node controller hasn't heard from node within node-monitor-grace-period), `MemoryPressure`, `DiskPressure`, `PIDPressure`; `.spec.unschedulable=true` = cordoned. PromQL: `kube_node_status_condition{condition="Ready",status="true"} == 0`, `kube_node_spec_unschedulable == 1`. Mixin alert **KubeNodeNotReady** (for: 15m, warning): `kube_node_status_condition{condition="Ready",status="true"} == 0 and on (cluster, node) kube_node_spec_unschedulable == 0` - note it deliberately excludes cordoned nodes, encoding "cordoned = expected maintenance" into the alert itself.
- **Healthy:** all nodes `Ready=True`, all pressure conditions `False`, no unexpected `unschedulable`. Pressure conditions also add taints (`node.kubernetes.io/memory-pressure`, `.../disk-pressure`) that block scheduling and trigger eviction.
- **Maintenance signal:** cordoned/`SchedulingDisabled` nodes plus an `Updating` MCP (A4) = node is being drained for an OS/config rollout, not broken.
- Sources: [Kubernetes Nodes concepts](https://kubernetes.io/docs/concepts/architecture/nodes/), [Node status reference](https://v1-34.docs.kubernetes.io/docs/reference/node/node-status), [kubernetes-mixin alerts](https://monitoring.mixins.dev/kubernetes/)

### A4. MachineConfigPools (the OCP "nodes are rolling" signal)
- **Query:** `oc get mcp` (columns UPDATED / UPDATING / DEGRADED, plus MACHINECOUNT / READYMACHINECOUNT / UPDATEDMACHINECOUNT / DEGRADEDMACHINECOUNT); conditions `Updated`, `Updating`, `Degraded`, `NodeDegraded`, `RenderDegraded`; `.spec.paused=true` = pool paused (updates deliberately held, e.g. canary strategy - but a paused pool blocks MCO and can even degrade the machine-config CO and block cert rotation if left paused).
- **Healthy steady state:** `Updated=True`, `Updating=False`, `Degraded=False`, `DegradedMachineCount=0`. **Maintenance state:** `Updating=True` - nodes are being cordoned/drained/rebooted one by one for a MachineConfig or OCP upgrade; expect transient NotReady/SchedulingDisabled nodes. **Broken:** `Degraded=True` (e.g. "unexpected on-disk state") requires intervention and will stall upgrades.
- Sources: [KCS: Degraded machine-config CO due to paused MCP](https://access.redhat.com/solutions/5317441), [KCS: MCP stuck degraded after modification](https://access.redhat.com/solutions/5244121), [KCS: MCP degraded "unexpected on-disk state"](https://access.redhat.com/solutions/5598401), [Canary rollout with custom MCPs](https://docs.okd.io/4.12/updating/update-using-custom-machine-config-pools.html)

### A5. etcd health
- **Query (endpoints):** `oc rsh -n openshift-etcd <etcd-pod>` then `etcdctl endpoint health` / `endpoint status`; PromQL:
  - Members up: `sum(up{job="etcd"})` vs expected 3; alert **etcdMembersDown**, **etcdInsufficientMembers** (quorum lost, ~3m).
  - Leader: `etcd_server_has_leader == 0` for 1m fires **etcdNoLeader** - no reads/writes possible.
  - Leader churn: `increase(etcd_server_leader_changes_seen_total[15m])` (frequent elections = disk/network trouble; alert etcdHighNumberOfLeaderChanges).
  - Disk: `histogram_quantile(0.99, sum by (instance, le) (irate(etcd_disk_wal_fsync_duration_seconds_bucket{job="etcd"}[5m])))` - healthy < 10ms; sustained high p99 fires **etcdHighFsyncDurations** and causes leader elections and slow API. Also `etcd_disk_backend_commit_duration_seconds_bucket` (p99 < 25ms) and **etcdGRPCRequestsSlow**.
- **Why:** every write is fsync'd by leader and quorum peers (Raft); slow disk on one member degrades the whole control plane.
- Sources: [openshift/runbooks etcdHighFsyncDurations](https://github.com/openshift/runbooks/blob/master/alerts/cluster-etcd-operator/etcdHighFsyncDurations.md), [etcdNoLeader](https://github.com/openshift/runbooks/blob/master/alerts/cluster-etcd-operator/etcdNoLeader.md), [etcdInsufficientMembers](https://github.com/openshift/runbooks/blob/master/alerts/cluster-etcd-operator/etcdInsufficientMembers.md), [etcdMembersDown](https://github.com/openshift/runbooks/blob/master/alerts/cluster-etcd-operator/etcdMembersDown.md), [Recommended host practices](https://docs.okd.io/4.9/scalability_and_performance/recommended-host-practices.html)

### A6. Firing alerts (Alertmanager / ALERTS metric)
- **Query:** PromQL `ALERTS{alertstate="firing", severity="critical"}` (exclude the deadman: `ALERTS{alertname!="Watchdog", alertstate="firing", severity=~"critical|warning"}`), or Alertmanager API `GET /api/v2/alerts` on `alertmanager-main` in `openshift-monitoring` (Thanos Querier for the ALERTS series). Real-world example pattern from IBM/OCP ops docs: `ALERTS{alertname!~"Watchdog|...", alertstate="firing"} >= 1`.
- **Healthy:** zero firing critical alerts; **Watchdog MUST be firing** - it is `vector(1)`, always true, severity `none`; its absence means the monitoring/alerting pipeline itself is broken (dead man's switch, e.g. PagerDuty DeadMansSnitch integration). An automated attestor should treat "no Watchdog" as "cluster observability unattestable".
- Sources: [Watchdog runbook (kube-prometheus)](https://runbooks.prometheus-operator.dev/runbooks/general/watchdog/), [OCP Managing alerts](https://docs.redhat.com/en/documentation/openshift_container_platform/4.11/html/monitoring/managing-alerts), [IBM OpenShift monitoring page with ALERTS query example](https://www.ibm.com/support/pages/openshift-monitoring)

### A7. API server availability / error rate
- **Query:** kubernetes-mixin SLO framework: recording rule `apiserver_request:availability30d` (99% over rolling 30d) built on `apiserver_request_total` + slow-request buckets; multiwindow multi-burn-rate alert **KubeAPIErrorBudgetBurn**, e.g. critical: `sum by(cluster) (apiserver_request:burnrate1h) > (14.40 * 0.01) and sum by(cluster) (apiserver_request:burnrate5m) > (14.40 * 0.01)`. Simple direct checks: `sum(rate(apiserver_request_total{code=~"5.."}[5m])) / sum(rate(apiserver_request_total[5m]))` (healthy: <1%) and `up{job="apiserver"}`.
- **Why:** API errors/slowness break reconciliation cluster-wide; error-budget burn is the standard SLO-based signal (errors counted = 5xx plus too-slow responses).
- Sources: [KubeAPIErrorBudgetBurn runbook (openshift/runbooks)](https://github.com/openshift/runbooks/blob/master/alerts/cluster-kube-apiserver-operator/KubeAPIErrorBudgetBurn.md), [kube-prometheus runbook](https://runbooks.prometheus-operator.dev/runbooks/kubernetes/kubeapierrorbudgetburn/), [Povilas Versockas: K8s API server SLO alerts](https://povilasv.me/kubernetes-api-server-slo-alerts-the-definitive-guide/), [kubernetes-mixin](https://monitoring.mixins.dev/kubernetes/)

### A8. Capacity / saturation
- **Query:** mixin alerts **KubeCPUOvercommit** / **KubeMemoryOvercommit** (for: 10m): `sum(namespace_cpu:kube_pod_container_resource_requests:sum)` vs `sum(kube_node_status_allocatable{resource="cpu"})` minus the largest node (i.e. "can the cluster survive losing one node"). Direct ratios: `sum(kube_pod_container_resource_requests{resource="cpu"}) / sum(kube_node_status_allocatable{resource="cpu"})` and same for `memory`. Pod-count saturation: `sum(kubelet_running_pods)` or count of scheduled pods vs `sum(kube_node_status_capacity{resource="pods"})` (mixin alert KubeletTooManyPods at >95% of max pods per node).
- **Healthy:** requests fit within allocatable-minus-one-node; pod count comfortably under max-pods (default 250/node on OCP).
- Sources: [kubernetes-mixin resource_alerts.libsonnet](https://github.com/kubernetes-monitoring/kubernetes-mixin/blob/master/alerts/resource_alerts.libsonnet), [monitoring.mixins.dev/kubernetes](https://monitoring.mixins.dev/kubernetes/)

### A9. Pending CSRs and certificate expiry
- **Query:** `oc get csr` - any `Pending` CSRs of types `kubernetes.io/kube-apiserver-client-kubelet` (client) or `kubernetes.io/kubelet-serving` (serving). Bulk approve: `oc get csr -o name | xargs oc adm certificate approve`. Cert expiry PromQL: mixin alert **KubeClientCertificateExpiration** on `apiserver_client_certificate_expiration_seconds` histogram (warning <7d, critical <24h).
- **Healthy:** zero pending CSRs; no cert-expiry alerts. Kubelet CSRs are requested 105-35 days pre-expiry; unapproved CSRs eventually drive nodes NotReady ("Unauthorized" on CSR creation is a known failure mode). Note: there is no built-in alert for the default ingress certificate nearing expiry (open RFE-4269); orgs monitor app/route certs via cert-manager or custom exporters.
- Sources: [KCS: Node NotReady due to Unauthorized CSR](https://access.redhat.com/solutions/5044281), [KCS: Investigating OpenShift CSR issues](https://access.redhat.com/solutions/3716861), [KubeClientCertificateExpiration runbook](https://runbooks.prometheus-operator.dev/runbooks/kubernetes/kubeclientcertificateexpiration/), [OCP certificate types](https://docs.redhat.com/en/documentation/openshift_container_platform/4.8/html/security_and_compliance/certificate-types-and-descriptions), [KCS: renew expired default ingress certificate](https://access.redhat.com/solutions/6458661)

### A10. Red Hat Insights / OCM, and "is the cluster in maintenance"
- **Insights/OCM:** the in-cluster Insights Operator uploads telemetry; Insights Advisor (Hybrid Cloud Console / OpenShift Cluster Manager) continuously evaluates it against a recommendation database and surfaces issues grouped by risk (low/moderate/important/critical) affecting availability, fault tolerance, performance, security. This is Red Hat's own automated "cluster health attestation" - an agent can mirror its role locally. Sources: [Remote health monitoring with connected clusters](https://docs.redhat.com/en/documentation/openshift_container_platform/4.11/html/support/remote-health-monitoring-with-connected-clusters), [Using Insights Advisor](https://docs.okd.io/4.17/support/remote_health_monitoring/using-insights-to-identify-issues-with-your-cluster.html)
- **Maintenance signals (composite):** ClusterVersion `Progressing=True` (upgrade), any MCP `Updating=True` or `paused=true`, nodes cordoned (`kube_node_spec_unschedulable==1`) while their MCP updates, and - for managed clusters (ROSA/OSD) - an upgrade policy/maintenance window scheduled in OCM (SRE-managed upgrades run inside customer-defined windows; a missed window is auto-cancelled). Sources: [ROSA upgrade via OCM/CLI](https://cloud.redhat.com/learning/learn:getting-started-red-hat-openshift-service-aws-rosa/resource/resources:upgrading-red-hat-openshift-service-aws-cluster-using-cli-or-console), [KCS: ROSA/OSD upgrade maintenance cancelled](https://access.redhat.com/solutions/6648291), [KCS: OCP4 upgrade pre-checks](https://access.redhat.com/solutions/7004992)

## B. APPLICATION 360 HEALTH (per namespace/app, deterministic)

All metrics are kube-state-metrics (`job="kube-state-metrics"`) unless noted; verified against [KSM pod-metrics docs](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/metrics/workload/pod-metrics.md) and [kubernetes-mixin](https://monitoring.mixins.dev/kubernetes/).

1. **Workload availability**
   - Deployments: `kube_deployment_spec_replicas > kube_deployment_status_replicas_available` sustained = mismatch. Mixin **KubeDeploymentReplicasMismatch** (for: 15m): `(kube_deployment_spec_replicas > kube_deployment_status_replicas_available) and (changes(kube_deployment_status_replicas_updated[10m]) == 0)` - the `changes()` guard excludes in-progress rollouts.
   - StatefulSets: **KubeStatefulSetReplicasMismatch**: `(kube_statefulset_status_replicas_ready != kube_statefulset_replicas) and (changes(kube_statefulset_status_replicas_updated[10m]) == 0)`.
   - DaemonSets: **KubeDaemonSetRolloutStuck** (current/updated/available vs `kube_daemonset_status_desired_number_scheduled`, plus `kube_daemonset_status_number_misscheduled != 0`).

2. **Pod pathology**
   - CrashLoopBackOff: `max_over_time(kube_pod_container_status_waiting_reason{reason="CrashLoopBackOff"}[5m]) >= 1` (mixin **KubePodCrashLooping**, for: 15m). Restart churn: `increase(kube_pod_container_status_restarts_total[1h]) > 3`.
   - Image problems and other waits: **KubeContainerWaiting**: `kube_pod_container_status_waiting_reason{reason!="CrashLoopBackOff"} > 0` for 1h; filter `reason=~"ImagePullBackOff|ErrImagePull|CreateContainerConfigError|CreateContainerError"` for faster deterministic checks.
   - OOMKilled: `kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1` (gauge persists after recovery - pair with a restart-rate check to distinguish "currently OOM-looping" from "OOMed once, recovered"). Labels on all three: `namespace, pod, container, reason, uid`.

3. **Pending / unschedulable pods**
   - `kube_pod_status_phase{phase="Pending"} == 1` sustained; `kube_pod_status_unschedulable == 1` (PodScheduled=False, reason Unschedulable). Mixin **KubePodNotReady** (for: 15m) uses `kube_pod_status_phase{phase=~"Pending|Unknown|Failed"}` joined with `kube_pod_owner{owner_kind!="Job"}` to exclude finished Jobs - copy that join in a checks.yaml to avoid Job false positives.

4. **Recent Warning events**
   - Not in kube-state-metrics; query the API: `oc get events -n <ns> --field-selector type=Warning --sort-by=.lastTimestamp` (typical reasons: FailedScheduling, BackOff, Unhealthy, FailedMount, FailedCreatePodSandBox). This is the standard non-metric complement for "why" after a metric check fails.

5. **Quota, limits vs usage, throttling**
   - Quota: `kube_resourcequota{type="used"} / ignoring(instance, job, type) (kube_resourcequota{type="hard"} > 0) > 0.9` (mixin **KubeQuotaAlmostFull**).
   - Memory headroom: `container_memory_working_set_bytes{container!=""}` (cAdvisor) vs `kube_pod_container_resource_limits{resource="memory"}`; ratio > ~0.9 = OOM risk.
   - CPU throttling: mixin **CPUThrottlingHigh** (for: 15m, info): `sum(increase(container_cpu_cfs_throttled_periods_total{container!=""}[5m])) ... / sum(increase(container_cpu_cfs_periods_total[5m])) ... > (25/100)` grouped on `(cluster, namespace, pod, container, instance)`.

6. **HPA at max:** **KubeHpaMaxedOut** (for: 15m): `kube_horizontalpodautoscaler_status_current_replicas == kube_horizontalpodautoscaler_spec_max_replicas` (known false positive when min==max - exclude that case).

7. **PDB:** disruptions allowed: `kube_poddisruptionbudget_status_pod_disruptions_allowed == 0` means node drains (maintenance!) will block; mixin **KubePdbNotEnoughHealthyPods**: `(kube_poddisruptionbudget_status_desired_healthy - kube_poddisruptionbudget_status_current_healthy) > 0`.

8. **PVC usage (kubelet, not KSM):** **KubePersistentVolumeFillingUp** critical: `(kubelet_volume_stats_available_bytes / kubelet_volume_stats_capacity_bytes) < 0.03 and kubelet_volume_stats_used_bytes > 0`; warning adds `predict_linear(kubelet_volume_stats_available_bytes[6h], 4*24*3600) < 0` (full within 4 days). Inode variant: `kubelet_volume_stats_inodes_free / kubelet_volume_stats_inodes`.

9. **Route/Ingress + cert expiry:** per-route traffic/errors via OCP router HAProxy metrics `haproxy_server_http_responses_total{code="5xx", exported_namespace="<ns>", route="<route>"}` (the console's route charts use it; per-server export silently stops above `ROUTER_METRICS_HAPROXY_SERVER_THRESHOLD`=500 backends - use `haproxy_backend_http_responses_total` or shard). Route TLS cert expiry has no built-in alert (RFE-4269); standard practice is cert-manager (Operator 1.13+ can manage ingress certs) or a cert exporter. Sources: [openshift/router haproxy metrics source](https://github.com/openshift/router/blob/master/pkg/router/metrics/haproxy/haproxy.go), [router metrics debugging gist](https://gist.github.com/felixkrohn/c659872f18fbda4fdbd709fbdcd18bbd), [cert types doc](https://docs.okd.io/latest/security/certificate_types_descriptions/ingress-certificates.html)

10. **Golden signals + USE:** Google SRE's four golden signals - latency, traffic, errors, saturation ([SRE book ch. 6](https://sre.google/sre-book/monitoring-distributed-systems/)). Generic PromQL patterns (instrumented apps): traffic `sum(rate(http_requests_total{namespace="<ns>"}[5m]))`; errors `sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))`; latency `histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))`; for uninstrumented apps fall back to router metrics (above). Saturation via the [USE method](https://www.brendangregg.com/USEmethod/use-linux.html) (per resource: utilization, saturation, errors): CPU utilization `sum(rate(container_cpu_usage_seconds_total{container!=""}[5m]))` vs limits, saturation = throttling ratio (B5), memory = working set vs limit, errors = restarts/OOM.

## C. FLEET / MULTI-CLUSTER (100s of OCP clusters)

- **Aggregation architecture:** the standard Red Hat pattern is ACM Observability (MultiClusterObservability): each managed cluster runs an observability-endpoint-operator/metrics-collector that federates from the cluster's in-cluster Prometheus and pushes to a Thanos receive/query stack on the hub, backed by S3-compatible object storage; Grafana on the hub gives fleet-wide single pane. Plain Thanos (sidecar/receive + Querier) is the equivalent DIY pattern. Sources: [ACM Observability docs](https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_management_for_kubernetes/2.13/html-single/observability/index), [ACM observability service intro](https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_management_for_kubernetes/2.11/html/observability/observing-environments-intro)
- **Cluster identity labels:** ACM injects `cluster` (managed cluster name) and `clusterID` (OpenShift cluster UUID) as labels on every collected series; in generic Thanos setups the same role is played by Prometheus `external_labels` (conventionally `cluster`), which Thanos Querier requires for deduplication/fan-in. Every fleet PromQL should therefore `sum by (cluster, ...)` and filter `{cluster="..."}`. Note ACM collects a default metrics allowlist (ConfigMap `observability-metrics-allowlist`); `kube_pod_labels`/custom metrics may need to be added to the custom allowlist. Source: [ACM Observability docs (metrics collection, custom metrics allowlist)](https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_management_for_kubernetes/2.13/html-single/observability/index)
- **Finding where an app runs, fleet-wide:** kube-state-metrics converts Kubernetes labels to Prometheus labels with a `label_` prefix and non-alphanumeric characters sanitized to `_`, so `app.kubernetes.io/name=foo` becomes `label_app_kubernetes_io_name="foo"` and `app=foo` becomes `label_app="foo"`. Since KSM v2 this is opt-in via `--metric-labels-allowlist=pods=[app,app.kubernetes.io/name],namespaces=[...]` (OCP's cluster monitoring exposes a curated set). Discovery queries:
  - `count by (cluster, namespace) (kube_pod_labels{label_app_kubernetes_io_name="<app>"} or kube_pod_labels{label_app="<app>"})` - which clusters/namespaces run the app.
  - `count by (cluster, namespace) (kube_namespace_labels{label_<team_or_app_label>="<x>"})` - namespace-level ownership (metric confirmed: `kube_namespace_labels{namespace, label_NS_LABEL}`).
  - Join pattern to enrich health metrics with app identity: `kube_pod_container_status_restarts_total * on (namespace, pod, cluster) group_left(label_app_kubernetes_io_name) kube_pod_labels`.
  - Recommended label conventions: `app.kubernetes.io/name`, `app.kubernetes.io/instance`, `app.kubernetes.io/part-of` (Kubernetes recommended labels), legacy `app`.
  - Sources: [kube-state-metrics v2 announcement (label_/annotation_ prefixing, allowlist opt-in)](https://kubernetes.io/blog/2021/04/13/kube-state-metrics-v-2-0/), [KSM namespace metrics](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/metrics/cluster/namespace-metrics.md), [KSM pod metrics](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/metrics/workload/pod-metrics.md), [label prefix issue #2818 confirming sanitization behavior](https://github.com/kubernetes/kube-state-metrics/issues/2818)

## D. TRIAGE FLOW PRACTICE (industry summary)

- **Mitigate before root-causing.** Google SRE's troubleshooting loop is triage -> examine -> diagnose -> test/treat, and during an active incident the first duty is "stop the bleeding" (divert traffic, roll back, disable a subsystem), with root cause analysis deferred; response runs under an Incident Command structure with playbooks. ([Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/), [Emergency Response](https://sre.google/sre-book/emergency-response/), [Incident management guide](https://sre.google/resources/practices-and-processes/incident-management-guide/))
- **"Platform or app?" is the first fork, answered by layered attestation.** Standard practice (mirrored in Red Hat troubleshooting docs and OCP's own alert taxonomy) is: firing critical alerts + Watchdog present -> ClusterVersion/ClusterOperators -> nodes/MCPs -> etcd/API server -> only then descend into the namespace. If the platform attests healthy and no maintenance is in progress, the fault is presumed app-side; if an upgrade/MCP roll is in progress, app symptoms (pod restarts, single-replica blips) are re-scored as expected maintenance noise.
- **Deterministic checks first, exploration second.** First-level triage is a fixed checklist of condition/metric evaluations (sections A/B) with healthy criteria, like Brendan Gregg's USE checklist and Insights Advisor's rule engine - both are precedents for encoding checks as data (a checks.yaml) rather than ad hoc queries. ([USE method](https://www.brendangregg.com/USEmethod/use-linux.html), [Insights Advisor](https://docs.okd.io/4.17/support/remote_health_monitoring/using-insights-to-identify-issues-with-your-cluster.html))
- **Escalation carries standardized evidence.** Red Hat support's initial data gathering is `oc adm must-gather` (cluster-wide diagnostic dump run in a temp pod, attached to the case with cluster ID) and the narrower `oc adm inspect <resource>` when must-gather can't run or a single component is in scope; a first-level agent should end its run by producing or recommending exactly these artifacts. ([Gathering data about your cluster](https://docs.redhat.com/en/documentation/openshift_container_platform/4.16/html/support/gathering-cluster-data))
- **Alert-driven entry, SLO-based severity.** Mature fleets enter triage from an alert (severity `critical` pages, `warning` tickets, `info` ignored by default) and rate urgency by error-budget burn (multiwindow burn-rate as in KubeAPIErrorBudgetBurn) rather than raw thresholds; every shipped alert links a runbook (openshift/runbooks, runbooks.prometheus-operator.dev) - a convention the agent's checks should replicate with a `runbook_url` per check. ([kube-prometheus runbooks](https://runbooks.prometheus-operator.dev/runbooks/kubernetes/kubeapierrorbudgetburn/), [openshift/runbooks](https://github.com/openshift/runbooks))

**Notes for the checks.yaml:** the mixin `for:` durations (15m for most workload checks, 10m rollout-guard windows) and its false-positive guards (exclude cordoned nodes in KubeNodeNotReady, exclude Jobs in KubePodNotReady, exclude in-progress rollouts via `changes(...[10m]) == 0`, HPA min==max case) are hard-won defaults worth copying verbatim; treat Watchdog-absent, monitoring CO degraded, and stale `cluster` series on the fleet hub as "cannot attest" states distinct from "unhealthy".
